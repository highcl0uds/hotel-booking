# ADR-0003. Устойчивость вызовов Hotel Service: Timeout + Retry + CircuitBreaker

## Контекст

ТЗ требует тайм-аут и ограниченное число повторов с растущим интервалом для удалённых вызовов, а по исчерпании попыток — компенсацию. Кроме того, недоступный Hotel Service не должен держать потоки Booking Service.

## Решение

Клиент собран из двух слоёв (паттерн «декоратор», оба реализуют интерфейс `HotelClient`):

- **`RestHotelClient`** — одна HTTP-попытка через `RestClient`, адрес `lb://hotel-service` разрешается через Eureka. Тайм-ауты: соединение 1 с, ответ 2 с. Исход переводится в исключения:
  - 404/409 → `SlotRejectedException` (отказ, повторять не нужно);
  - 5xx, тайм-ауты и ошибки соединения → `HotelUnavailableException` (исход неизвестен);
  - прочие 4xx → `HotelIntegrationException`.
- **`ResilientHotelClient`** — Resilience4j:
  - `Retry`: 3 попытки, экспоненциальная пауза 200 → 400 мс, повторяется только `HotelUnavailableException`.
  - `CircuitBreaker`: окно из 10 вызовов, порог отказов 50 %, 10 с в состоянии OPEN, затем пробные вызовы. Отказы 409/404 не считаются сбоями.
  - Порядок вложенности: Retry(CircuitBreaker(вызов)), то есть каждая попытка учитывается circuit breaker'ом. При открытом breaker'е повторов нет, Booking сразу отвечает `503 HOTEL_UNAVAILABLE` и выполняет компенсацию.

Параметры вынесены в `application.yml` (`resilience4j.*`, `app.hotel-client.*`). События повторов и смены состояния breaker'а пишутся в лог с `bookingId`.

## Плюсы и минусы

- (+) Время ответа ограничено даже при зависшем Hotel Service.
- (+) Повторы безопасны благодаря идемпотентности (ADR-0002).
- (−) Худший случай для одной брони — около 3 × 2 с плюс паузы, после чего бронь отменяется.
